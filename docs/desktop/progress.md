## M1 — shell desktop Electron

Estado: concluído em 2026-10-24. PR: https://github.com/Stoltembergg/Office-Bots/pull/1. O shell inicia o servidor em `127.0.0.1` numa porta escolhida pelo sistema, espera o listener ficar pronto antes de criar a janela e guarda estado em `userData`. O perfil desktop desliga World, acesso remoto, atualização web e migração do diretório legado. A janela usa sandbox, context isolation e preload mínimo; o IPC só expõe a versão do app e valida origem, frame principal e `webContents`.

Commits do shell: `feat: add Electron desktop shell`. O CI identificou que o maker Squirrel não tinha o campo obrigatório de autores; `desktop/forge.config.ts` agora informa `authors: 'Office Bots contributors'` (commit `586493ea246ce310e4cde9e645f071a5761b79ef`).

O bootstrap passou para `server/app.ts`; `server/index.ts` continua sendo a entrada web de `npm start`. Foram adicionados os alvos `desktop:dev`, `desktop:build`, `desktop:package`, `desktop:test` e `desktop:typecheck`, Electron `45.0.0` e Forge `8.0.1`. O pacote inclui cliente, main e preload no ASAR; diretório de dados fica fora dele.

Validação local Linux x64, Node 24.19.0/npm 11.9.0: `npm run typecheck`, `npm run desktop:test` (11 testes), `npm test` (162 arquivos; 1.893 passaram, 2 skipped), `npm run desktop:package` e `npm start` em smoke web passaram. O Forge gerou um ZIP Linux. O ASAR contém `dist/client/index.html`, `dist/desktop/main.mjs`, `dist/desktop/preload.cjs` e `package.json`.

CI GitHub Actions, Node 22.19.0: `npm ci`, `npm run typecheck`, `npm run desktop:test`, `npm run desktop:package` e smoke do pacote passaram em Ubuntu x64, Windows x64, macOS arm64 e macOS Intel. O job `verificar` também passou (`npm test` e `npm run build`).

Limite local: a janela empacotada não pôde ser aberta neste container porque a política do sistema bloqueia o socket Unix usado por `app.requestSingleInstanceLock()` (`socket() failed: Operation not permitted`). O smoke do executável passou nos runners nativos da matriz. Assinatura dos instaladores, notarização macOS e QA manual de instalação permanecem para M6; estes checks não comprovam tais etapas. A revisão também corrigiu a ordem de cleanup na falha do Vite, a precedência de `dev: false` e o padrão web para `HABBLAUD_PORT=0`.

## M2.1 — catálogo persistente de projetos e agentes

Escopo: primeiro incremento do M2, na branch `feat/persistent-agent-catalog`, baseado no HEAD `f8896c7` do PR #1 (ainda aberto). Cadastro versionado em `catalog.json`, referências de projeto validadas, pasta canônica, política de modelo por agente, arquivamento preservando identidade e bloqueio de edição enquanto o runtime informar turno ativo. O consumidor deve fornecer a consulta síncrona de ocupação ao construir o store. Nenhuma inferência, conta, rota HTTP ou IPC foi adicionada.

Decisão: compartilhar um catálogo versionado para projetos e agentes, com lock exclusivo por diretório e substituição atômica por rename. Colisão de writer falha sem sobrescrever; lock deixado por crash requer resolução explícita após confirmar que o processo terminou. Arquivo inválido ou versão desconhecida é preservado e bloqueia gravações. Recuperação/quarentena e sessões serão entregues em incrementos posteriores.

M2 permanece em andamento: worker Pi, conversas, fila, deduplicação de mensagens e integração do guard de arquivamento ao início de turno ainda não foram implementados. O serviço de cadastro não está conectado à interface nesta etapa.

Validação M2.1 em Linux x64, Node 24.19.0/npm 11.9.0: teste novo falhou inicialmente pela ausência do catálogo; após implementação, 9/9 testes de catálogo passaram. `npm run typecheck`, `npm test` (1.902 passaram, 2 skipped) e `npm run build` passaram. `git diff --check` passou. O checker i18n encontrou somente a lacuna preexistente do M1 `Encerrando o servidor desktop/web…` nos três idiomas; o novo erro de cadastro tem traduções en/es/fr.

Revisão independente do incremento: sem achados bloqueantes. Limitações preservadas: rename fornece substituição atômica, sem garantia de durabilidade contra perda de energia (sem fsync); o futuro SessionManager deverá serializar admissão de turnos e mutações do catálogo — a consulta síncrona de ocupação sozinha não impede corrida com um turno iniciado durante a gravação assíncrona. A resolução de modelo na conversa, os locks de sessão e a recuperação continuam no M2.

## M2.2 — conversas e escalonamento de turnos

Base: `da75a1f` do PR #2; branch `feat/managed-session-scheduler`. Entrega um SessionManager em memória e a interface interna ManagedRuntime, ainda sem adaptador Pi, IPC, HTTP ou UI. Criar conversa fixa identidade, cwd, instruções e seleção do agente sem inferência. Políticas fixed rejeitam override divergente; choose-on-start exige seleção válida. Disponibilidade de conta/modelo é uma função injetada, verificada na criação e antes da execução, sem fallback. Edição do agente só muda novas conversas.

O manager limita a dois turnos globais e um por agente, mantém fila consultável por list/get e deduplica messageId por conversa durante a vida do processo. Reusar ID com texto diferente é recusado. Um novo ID é necessário para tentar novamente após falha/cancelamento: não há repetição automática. Cancelar fila não chama runtime; cancelamento ativo mantém reserva até prompt e pedido de cancelamento terminarem. close bloqueia novos prompts, espera término e permite nova tentativa explícita após falha transitória de cleanup.

Decisão: acrescentar estado queued ao contrato para tornar a fila observável. A admissão usa o mesmo lock/fila do catálogo e registra ocupação sincronamente antes de liberar o lock. O app deve compartilhar um único catálogo/manager e fornecer `id => manager.isAgentBusy(id)` ao CatalogStore. Outros processos/instâncias com consultas de ocupação independentes não compartilham esse controle; a montagem definitiva no app ocorrerá com o worker.

Revisão independente identificou duas falhas importantes, ambas reproduzidas antes da correção: cancel pendente liberava a sessão cedo, podendo atingir um turno posterior; close falho retinha a Promise rejeitada e impedia retry. Testes RED→GREEN agora cobrem espera pelo cancel atrasado, ausência de reutilização/close prematuro, retry de close/cancel falhos e manutenção da barreira de admissão. Erros do runtime são convertidos em SessionError com códigos internos, sem propagar mensagens brutas ao futuro renderer.

Verificação Linux x64, Node 24.19.0/npm 11.9.0: 17 testes novos do manager, 26/26 em server/agents; suíte completa com 1.919 aprovados e 2 skipped; `npm run typecheck`, `npm run build` e `git diff --check` passaram. Nenhum modelo real foi chamado. Persistência/reabertura de conversas, recuperação após crash, envelopes de eventos e Pi worker continuam pendentes no M2; sem essas etapas, deduplicação não sobrevive a reinícios. O supervisor futuro deverá fazer prompt rejeitar quando o worker morrer, mantendo o princípio de não liberar concorrência enquanto houver execução de estado desconhecido.

## M2.3 — índice persistente de conversas

Base: `e183059` (PR #3 integrado na branch do catálogo); branch `feat/persistent-session-index`. O SessionStore guarda `sessions.json` em userData: identidade da conversa/agente/projeto, origem managed-pi, referência opaca do SDK, seleção efetiva de conta/provedor/modelo e estado. Não guarda transcript, prompt, credencial ou caminho de contexto. Conversas antigas preservam sua seleção após editar ou arquivar o agente. IDs e referências SDK duplicados e referências de catálogo ausentes/cruzadas são recusados.

Gravações serializadas, lock exclusivo por diretório, arquivo temporário 0600 e substituição por rename. Colisão de lock não remove o lock alheio. Arquivo truncado/schema inválido é copiado para quarentena mantendo o original bloqueado; nenhuma tentativa subsequente cria índice vazio silenciosamente. Versões desconhecidas e referências inválidas são preservadas e bloqueiam mutações. Falhas retornam códigos sanitizados. A referência do SDK será validada pelo adaptador no momento da retomada explícita; o índice não interpreta IDs como caminhos.

Decisão: entregar o store separadamente antes de conectá-lo ao SessionManager, para manter o incremento revisável sem alegar retomada segura antes do contrato do SDK. Custo: o manager atual continua em memória, sem persistência de turnos/deduplicação, e a UI ainda não usa o índice. A integração deverá persistir estado antes de executar e nunca reenfileirar trabalho durante recuperação. `recover()` é startup-only, antes de sessões vivas: queued/running/cancelling viram interrupted; idle/error/closed são preservados. A rotina não possui runtime e não pode executar inferência.

Decisão: schema 1 é o primeiro formato real de índice de conversas. Não foi inventada migração de um formato anterior inexistente; versões futuras são rejeitadas. Custo: futuras mudanças de schema exigirão migração e teste próprios, mantendo o item abrangente M2 pendente. Locks deixados por crash exigem resolução explícita após confirmar saída do proprietário; rename não garante durabilidade contra perda de energia (sem fsync), como no catálogo.

Verificação em Linux x64, Node 24.19.0/npm 11.9.0: teste inicialmente falhou pela ausência do módulo; 12 testes novos, 38/38 em server/agents, suíte completa 1.931 aprovados e 2 skipped; `npm run typecheck`, `npm run build` e `git diff --check` passaram. Revisão independente sem achados bloqueantes. Minor adiado: leituras repetidas de índice corrompido geram múltiplas cópias de quarentena; limitar/deduplicar antes de integrar polling da UI. Nenhuma chamada real de modelo. Pi worker, persistência coordenada do manager, validação/retomada do histórico SDK, eventos e recuperação integrada seguem pendentes; M2 não está concluído.

## M2.4 — persistência coordenada no gerenciador

Base: `1d5e7a8` (merge do PR #4 na branch do catálogo); branch `feat/durable-session-manager`. SessionManager agora exige um SessionStore. `initialize()` recupera o índice uma única vez; create aguarda a mesma Promise antes de criar recursos. A conversa só fica disponível após add persistido; se add falhar, o recurso recém-criado recebe close sem executar inferência.

Admissão mantém reserva por agente enquanto queued é persistido. O runtime só recebe prompt após running persistido; conclusão/erro/cancelamento só liquidam a Promise do turno após persistir estado terminal. A reserva e o slot permanecem até essa finalização terminar, com barreira que impede cancel tardio de alcançar outro turno. Cancelamento ativo pede parada imediatamente em paralelo à escrita de cancelling e aguarda ambas as operações; falha de disco não antecipa a liberação de cancel pendente. Close persiste closed e conserva a barreira de envios se falhar.

Decisão: conversas recuperadas ficam destacadas do runtime (detached), consultáveis com sua seleção original; prompt retorna resume-required. Fechá-las altera apenas o índice, sem usar um handle inexistente no worker. Custo: continuar essas conversas exige a futura retomada explícita e validada pelo Pi; nenhum histórico SDK é carregado por este incremento. MessageId continua deduplicado em memória; após reinício, a barreira de retomada impede reenvio acidental. O futuro resume deve reconciliar IDs/resultados com o SDK antes de liberar envios.

Decisão: falha de persistência bloqueia novos prompts naquela conversa até recuperação explícita/reinício. Falha de gravação terminal produz interrupted em memória e rejeita a Promise; não informa sucesso nem repete o efeito. Custo: uma conversa com disco reparado ainda exige recuperação antes de voltar a enviar. O SDK continua dono do contexto; o índice permanece schema 1, sem prompts/transcripts ou credenciais. A montagem no Electron, Pi worker, eventos e resume continuam pendentes no M2. A instância única do app deve compartilhar catálogo/manager/store; initialize não deve ser usado por um segundo manager enquanto o primeiro estiver executando.

Revisão independente encontrou duas falhas importantes, reproduzidas em testes antes da correção: pump retirava turno cancelado/finalizando da fila durante commit terminal, deixando índice running; retry de close após falha de disco descartava novamente um handle já fechado. Corrigidas com filtro de finalização/cancelamento no pump e marcação de recurso destacado imediatamente após close confirmado. Ambos os testes passaram RED→GREEN; nenhuma idempotência não documentada é exigida do runtime.

Verificação final em Linux x64, Node 24.19.0/npm 11.9.0: 17 testes novos de integração da persistência; 55/55 em server/agents; suíte completa com 1.948 aprovados e 2 skipped. `npm run typecheck`, `npm run build` e `git diff --check` passaram após as duas correções. Cobertura inclui startup corrompido, seleção anterior preservada, estados persistidos antes/depois do prompt, falha de disco, cancel atrasado, reserva durante commit terminal, retry de close e ausência de replay/handles fabricados. Nenhuma chamada real de modelo nem alteração de rotas/IPC/UI. O próximo incremento será o contrato de execução/eventos e o worker Pi; a retomada real continua bloqueada até qualificação e reconciliação do contexto SDK.

## M2.5 — processo Pi e eventos de turnos

Base: `45e23cc` (merge do PR #5 na branch do catálogo); branch `feat/pi-worker-events`. Pi SDK e pi-ai fixados em 1.4.0 como dependências de produção, com lockfile atualizado e requisito Node >=22.19 preservado. O build desktop agora produz `dist/desktop/pi-worker.mjs`; somente o worker importa o SDK. PiRuntime implementa ManagedRuntime usando processo filho e IPC interno validado. Não há rotas HTTP, preload ou montagem no Electron/manager ainda.

Eventos discriminados e validados: origem managed-pi, sessionId do app, runId único por turno, seq crescente por conversa e timestamp; message-start, text-delta, usage, message-end, state e códigos de erro sanitizados. Tipos/objetos privados do SDK não atravessam o contrato. Prompt só resolve depois do SDK terminar; cancel/close podem entrar enquanto prompt aguarda e close preserva o arquivo de contexto do SDK. Ao morrer ou perder IPC, o processo é encerrado; pending é rejeitado após exit, sem liberar execução incerta nem reiniciar/repetir mensagens. O host sintetiza um terminal de erro se a queda interromper um turno sem terminal.

Decisão: implementar primeiro o seam executável do SDK e o contrato de texto/uso; ferramentas e eventos de aprovação ficam para M3. Não habilitar ferramenta, extensão, MCP, skill, contexto de projeto, compactação automática, retry nem aquecimento de cache. Instruções do agente são texto literal e não autorizam ferramentas. Custo: ainda não há edição de arquivos, comandos ou compactação de conversas longas. O índice do app permanece só com metadados; o SDK guarda o contexto em diretório próprio fora dos projetos.

Decisão: o worker padrão não autoriza nenhuma conta até existir o cofre/account resolver de M3. Credenciais ambiente/CLI não concedem acesso a contas do app, e o ambiente do filho exclui tokens, HOME e NODE_OPTIONS. Modelo e nível de raciocínio são validados exatamente; não aceitar clamps/fallbacks silenciosos. Custo: testes usam factory de ModelRuntime com provedor falso em entry separado, nunca credencial real; o app ainda não oferece chat pago/OAuth. O launcher é um fork do host Node; o lançamento com o Node embutido do Electron, sua montagem no supervisor/manager, resume e reconciliação de messageId continuam gates de integração, sem exigir Node externo no produto final.

Revisão independente encontrou duas falhas importantes, ambas reproduzidas RED→GREEN: DefaultResourceLoader lia APPEND_SYSTEM.md e tratava instruções como caminho mesmo com flags de bloqueio; foi substituído por ResourceLoader estritamente vazio, sem descoberta, com instruções literais. Perda de IPC sem saída deixava processo vivo/prompt pendente; o pai agora encerra o filho e aguarda exit antes de liquidar o turno. Teste de autorização assíncrona seguida de close também confirmou cancelamento sem chamada ao provedor.

Verificação final Linux x64, Node 24.19.0/npm 11.9.0: 13 testes novos (SDK real em processo filho com fauxProvider e mensagens inválidas de fixture), suíte completa 1.961 aprovados e 2 skipped; `npm run typecheck`, `npm run desktop:test` (24/24), `npm run desktop:package` e `git diff --check` passaram após as correções. ASAR contém worker e dependência SDK. O primeiro package falhou por destino out/ antigo não vazio; o pacote gerado anterior foi preservado fora do checkout e o build final passou em diretório livre. desktop:test inclui os testes Pi para execução pela matriz nativa de CI, ainda pendente para este PR. Não foi executado SDK em Node embutido do Electron nem smoke de janela local; geração do pacote não comprova essa integração, assinatura ou instaladores de outros SOs.

Integração do PR: direcionar a nova entrega à main para consolidar M2.1–M2.5. Os PRs #2–#5 foram mesclados nas respectivas branches de base; a main ainda continha somente M1. A base de implementação/revisão deste incremento continua 45e23cc e a suíte verifica a árvore acumulada. Nenhum merge foi realizado pelo agente.

## M2.6 — ciclo de vida dos agentes no Electron

Base: `21cfb9c` (PR #6 integrado na main); branch `feat/desktop-agent-lifecycle`. Electron main passa a iniciar um único serviço de agentes com catálogo/manager/store compartilhados em userData. O supervisor aguarda o worker ficar pronto antes de abrir a janela, reutiliza o serviço ao reabrir janela macOS e encerra somente os recursos que criou. Falha do servidor/janela limpa o worker mesmo se outra etapa do cleanup falhar.

PiRuntime aceita um executável definido pelo host confiável e inicia o filho com `ELECTRON_RUN_AS_NODE=1`, sem NODE_OPTIONS nem credenciais ambiente. No app, fork usa process.execPath (o Electron incluído), não um Node instalado pelo usuário. initialize confirma o handshake sem criar sessão/inferência. O smoke empacotado agora exige também criar/fechar uma sessão SDK sintética sem prompt, para testar o worker e os imports em ASAR com o runtime incluído.

O stop do serviço congela admissão sincronamente, cancela fila, encerra o processo e aguarda turnos, criações e fechamentos já iniciados liquidarem a persistência antes de retornar. Não despacha fila durante shutdown nem publica criação que atravessou a barreira de saída. Conversas de turnos interrompidos não são repetidas. Erros de inicialização do serviço são sanitizados. O serviço permanece interno ao main: nenhuma API nova HTTP/preload/UI nem autorização de conta foi adicionada.

Decisão: entregar a montagem e o launcher embutido antes de liberar resume. Inspeção da API fixa 1.4.0 confirmou que o SDK só cria JSONL depois da primeira mensagem e não persiste os messageId do app automaticamente. Custo: conversas recuperadas continuam em consulta/resume-required até reconciliar referência, seleção, instruções e IDs/resultados no histórico SDK; abrir uma referência sem esses controles poderia duplicar execução ou criar histórico vazio. Não foi implementado um resume parcial que liberasse envios.

Revisão independente identificou uma falha importante: shutdown absorvia erro de persistência do drain e confirmava saída limpa com índice ainda running. Teste reproduziu stop resolvendo enquanto prompt rejeitava storage; corrigido para propagar storage após drenar todos os trabalhos. O serviço anexa handlers imediatamente e aguarda stop + drain com allSettled, reportando erro somente após a saída efetiva do processo. Interrupções/cancelamentos esperados da parada não viram falso erro de disco.

Verificação final Linux x64: 11 testes novos; suíte completa 1.972 aprovados e 2 skipped; `npm run typecheck`, `npm run desktop:test` (35/35), `npm run desktop:package` e `git diff --check` passaram após a correção. Prova adicional com executável do pacote e entrada em app.asar carregou o SDK real, criou/fechou sessão sintética e encerrou o worker, sem inferência; Node embutido observado: 24.22.0. O smoke GUI reforçado será executado no CI nativo; a restrição local do socket de instância única do Electron continua impedindo abrir a janela neste container. Sem validação local Windows/macOS, assinatura ou notarização. Montagem interna concluída; UI, cofre/permissões e resume/reconciliação seguem pendentes.
